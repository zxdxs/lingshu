# 181 導覽：先修溢出，再談分組

## 量到的問題

導覽列原本是 21 個按鈕排成一列，放在 1,000px 寬的容器裡，但**內容實際寬 1,376px**；
用 `overflow-x:auto` 加『隱藏捲軸』，結果右側約 7 個按鈕（搜尋、方法、校勘、限制、我的、關於…）
**被藏起來，而且沒有任何視覺提示**。不同視窗寬度量到的都是同一個問題：

| 視窗 | 導覽可用寬 | 內容寬 | 高度 |
|---|---|---|---|
| 1280 | 1000 | 1376 | 50（單列、溢出） |
| 1100 | 1000 | 1376 | 50（溢出） |
| 900 | 900 | 1376 | 50（溢出） |
| 760 | 760 | 1376 | 50（溢出） |

## 這一輪只做了最安全的一半

改成 `flex-wrap: wrap`（移除隱藏捲軸），四個寬度量到的都是『內容寬＝可用寬』，高度 94px（兩行）。
21 個按鈕全部看得見，不動任何路由與測試（`#nav a` 仍是 21）。

## 分組值不值得做：值得，但有代價

### 方案 A：維持現狀（兩行）

- 優點：零風險、所有入口一眼看完、測試不動。
- 缺點：桌面上多佔 44px；手機上兩行仍偏擠（21 個 pill 是 21 個決策點）。

### 方案 B：五組下拉（推薦）

| 主項 | 收進去 |
|---|---|
| 首頁 | — |
| 讀 | 通讀、十二經、病候、變體、注家、九宫 |
| 學 | 主題、路徑、模組、通則 |
| 練 | 題庫、概念 |
| 比 | 異同、九鍼、校勘 |
| 更多 | 搜尋、方法、限制、我的、關於 |

- 用原生 `<details>` 做下拉：零 JS、可鍵盤操作、離線可用。
- 頂層 6 個按鈕約 500px，1,000px 容器內單行就夠。
- 代價：多一層點擊；手機要點開才知道有什麼；`#nav a` 數量與『一列看完全部』的體驗改變，
  需同步改 `smoke_browser` 的導覽數量斷言與截圖。

### 方案 C：精簡入口（不合併）

把重複性高的入口拿掉或併頁（例如「九鍼」併進「方法」、「概念」併進「主題」），
讓總數降到 14–16 個仍單行。代價是動到資訊架構，比 A 大、比 B 小，但會影響已有連結。

## 決定（2025-10-25）

暫時**維持方案 A（兩行）**：先把「被藏起來」修掉，觀察實際使用再說。
B（五組下拉）與 C（精簡入口）列在這裡，等有讀者回饋再動；那時也比較知道該把哪些連結收進哪一組。

## 建議順序

1. **先維持 A**（已修溢出），觀察一兩輪實際使用；導覽好不好用，看的是『讀者會不會找不到』，
   不是按鈕數量。
2. 若你或讀者反映『找不到某頁』，再上 B——那時也比較知道該把哪些連結收進哪一組。
3. C 不建議：它會改變既有連結的意義，而入口重複其實有幫助（同一頁可以從讀、學兩邊進）。

## 局限

一、兩行的導覽在 760px 以下會再折行（未量 3 行以上的情況）。
二、方案 B 的下拉在觸控裝置上需要點開，比一列直點多一步。
三、這些都是版面判斷，沒有使用者測試資料。
