# 182 反饋與聯繫：兩條路，一份清單

## 原本只有一個 email

`#/contact` 原本只列「郵箱」與相關站點，`data/聯絡.json` 還停在舊數字（1,031 題、708 卡）。
這一輪把「回報」當成一個正式入口來做。

## 兩條路

| 走法 | 適合 | 實作 |
|---|---|---|
| **GitHub Issue** | 單點勘誤、可公開、可追蹤、別人看得到已回報什麼 | `.github/ISSUE_TEMPLATE/勘誤.yml`（Issue 表單）＋ 站上直連 `issues/new?template=勘誤.yml` |
| **Email** | 附圖、長文、整份校勘表 | `mailto:` 已預填主旨與內文格式（篇序／句ID／原文／問題／版本） |

兩條路都寫在 `#/contact` 的新卡片『回報一處，就少一處』裡，並列出**回報時要附的五樣**。

## Issue 表單的欄位

問題類型（下拉：錯字／引文不符／句ID 掛錯／答案可議／注家節錄有誤／其他）、篇序（必填）、
句ID（選填）、原文照抄（必填）、問題與理由（必填）、你手上的版本、截圖或書影。
表單開頭就寫明『本站是訓練材料，不是定本』，並提醒先確認版本。

## 為什麼不自己做表單

本站是純靜態（GitHub Pages），沒有後端；自己刻表單要嘛送不出、要嘛得接第三方服務。
GitHub Issue 與 email 都是『不用維運就有紀錄』的路，且 Issue 讓回報可以被搜尋、被引用。

## 站上文案的更新

`data/聯絡.json` 的『最需要人幫忙的五件事』同步到現況：

1. 句ID 對應（1,068 題中 977 題已掛）
2. 待專家核（15 條整理語、6 道案例、注家配對）
3. 主題與概念分類
4. 太素對校空白
5. **新增**：注家節錄的校對（四家都是機器分離後節錄，未與影印本逐字校）

## 防線

`check_reader` 的 contact 檢查多三條：GitHub Issue 入口、`mailto:` 入口、回報清單五項都要出现在頁面，
少一個就紅。數字（977、15、6）仍由人工寫在 `data/聯絡.json`，未自動帶入——這點是缺口。

## 局限

一、email 是公開信箱，會有垃圾信；目前沒有自動過濾。
二、Issue 表單只在 GitHub 上生效，離線版（`reader/index.html`）看不到表單，只有 `mailto:`。
三、回報清單的五項是經驗值，沒有做過『照著填就能處理』的可用性測試。
